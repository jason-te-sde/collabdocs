# Operations

How to configure, run and recover CollabDocs. Design reasons are in [docs/design](design), the threat model in [SECURITY.md](../SECURITY.md).

CollabDocs is two Node processes and two data stores:

- the **web app** (`apps/web`, Next.js): pages, sign-in, the REST API, collaboration tokens;
- the **collab server** (`apps/collab`): Socket.IO, one live copy of every open document;
- **PostgreSQL**: users, documents, memberships, the update log and snapshots. The only durable store;
- **Redis**: relay between collab instances, membership messages, connection counters and the web app's rate-limit counters. Holds nothing that cannot be rebuilt.

`docker compose up -d` (see the README) starts PostgreSQL and Redis for development; the web app and the collab server run on the host. There is no container image for the two apps yet: build and start them with `npm run build` and `npm run start` on a host that has Node 22.12 or newer.

## Environment variables

### Secrets and addresses

Generate each secret with `openssl rand -base64 32`. The three secrets must all be different from each other.

| Variable                               | Used by     | Required                        | Meaning                                                                                                                                                                                                                                                                          |
| -------------------------------------- | ----------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                         | web, collab | yes                             | PostgreSQL connection string. The tests refuse a database whose name does not contain `test`.                                                                                                                                                                                    |
| `AUTH_SECRET`                          | web         | yes                             | Signs the Auth.js session cookie.                                                                                                                                                                                                                                                |
| `AUTH_URL`                             | web         | yes                             | The public URL of the web app (for example `https://docs.example.com`). Callback URLs are built from it.                                                                                                                                                                         |
| `AUTH_TRUST_HOST`                      | web         | behind a proxy                  | Set to `true` when the app runs behind a proxy that sets the host header.                                                                                                                                                                                                        |
| `COLLAB_TOKEN_SECRET`                  | web, collab | yes                             | Signs and verifies collaboration tokens. At least 32 bytes, different from `AUTH_SECRET`. The same value in the web app and every collab server. Anyone who has it can mint a token for any member document.                                                                     |
| `COLLAB_TOKEN_TTL_SECONDS`             | web         | no                              | Token lifetime, default 300, at most 900. A token is used once, at the handshake, so a short life costs nothing.                                                                                                                                                                 |
| `COLLAB_URL`                           | web         | no                              | Where the **browser** reaches the collab server, default `http://localhost:4000`. Read when a page is rendered, so one build serves any deployment. Use `wss`-capable `https://` in production.                                                                                  |
| `REDIS_URL`                            | web, collab | no                              | Enables several collab instances, cluster-wide connection limits and cluster-wide rate limits. Without it everything runs in one process.                                                                                                                                        |
| `REDIS_MESSAGE_SECRET`                 | web, collab | **whenever `REDIS_URL` is set** | Signs every relay frame and membership message (HMAC-SHA256). At least 32 bytes, different from `COLLAB_TOKEN_SECRET` and `AUTH_SECRET`, the same in the web app and every collab server. Both processes refuse to start with `REDIS_URL` and a missing, short or reused secret. |
| `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET` | web         | no                              | Both set: the GitHub sign-in button appears. Callback URL: `<AUTH_URL>/api/auth/callback/github`.                                                                                                                                                                                |
| `MAIL_TRANSPORT`                       | web         | in production                   | `console` (print), `file` (write to `MAIL_OUTBOX_DIR`) or a transport you add. Neither built-in one delivers mail. With it unset and `NODE_ENV=production` the app refuses to send.                                                                                              |
| `MAIL_OUTBOX_DIR`                      | web         | with `file`                     | Directory for the file mailer.                                                                                                                                                                                                                                                   |
| `RATE_LIMIT_PREFIX`                    | web         | no                              | Redis key prefix for the web app's rate-limit counters, default `collabdocs:rl:`.                                                                                                                                                                                                |

### Web app limits

| Variable                                | Default | Window     | What it limits                                                                                             |
| --------------------------------------- | ------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
| `AUTH_LIMIT_SIGNIN_PER_IP`              | 30      | 15 minutes | Sign-in attempts from one client address                                                                   |
| `AUTH_LIMIT_SIGNIN_PER_ACCOUNT`         | 10      | 15 minutes | Sign-in attempts for one email address, from anywhere                                                      |
| `AUTH_LIMIT_REGISTER_PER_IP`            | 10      | 1 hour     | Registrations from one client address                                                                      |
| `AUTH_LIMIT_REGISTER_PER_ACCOUNT`       | 3       | 1 hour     | Registrations for one email address                                                                        |
| `AUTH_LIMIT_VERIFY_RESEND_PER_ACCOUNT`  | 3       | 1 hour     | New verification links for one account                                                                     |
| `AUTH_LIMIT_INVITE_PER_USER`            | 30      | 1 hour     | Invitations one user sends                                                                                 |
| `AUTH_LIMIT_INVITE_PER_INVITER_ADDRESS` | 3       | 1 hour     | Invitations one member sends to one address                                                                |
| `AUTH_LIMIT_INVITE_MAIL_PER_ADDRESS`    | 5       | 1 hour     | Invitation mails to one address, all inviters together; past it the invitation stands and no mail is sent  |
| `TRUSTED_PROXY_HOPS`                    | 1       |            | How many proxies append to `X-Forwarded-For`. `0` ignores the header: every client then shares one address |

Every attempt counts, successful or not. The answer past a limit is HTTP 429 with `Retry-After` and the code `rate_limited`. Raise a limit when many real users share one address (an office, a university); lower it when the account key is the one being attacked. Run the web app behind a proxy that sets `X-Forwarded-For` and set `TRUSTED_PROXY_HOPS` to the number of proxies: without a proxy the per-address limits are one shared bucket for all clients.

### Collab server

| Variable                          | Default   | Meaning and how to tune it                                                                                                                                                      |
| --------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `COLLAB_PORT`, `COLLAB_HOST`      | 4000, all | Where it listens. `GET /healthz` answers 200 when it is up.                                                                                                                     |
| `COLLAB_CORS_ORIGIN`              | none      | Comma-separated browser origins allowed to connect. Set it to the web app's origin; with none set, browsers on other origins are refused.                                       |
| `COLLAB_TRUSTED_PROXY_HOPS`       | 0         | Proxies in front of the collab server that append to `X-Forwarded-For`. Leave at 0 only with no proxy; behind a load balancer set it, or all clients share the proxy's address. |
| `COLLAB_REDIS_CONNECT_TIMEOUT_MS` | 5000      | The server exits at start if Redis does not answer within this.                                                                                                                 |

| -------------------------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |

| `COLLAB_HANDSHAKE_BURST_PER_IP`, `COLLAB_HANDSHAKES_PER_SECOND_PER_IP`     | 100 burst, 5 per second         | The handshake is refused (`rate_limited`). | `COLLAB_MAX_CONNECTIONS_PER_USER`                                          | 8                               | The handshake is refused (`too_many_connections`). Counted across instances                                                   | Users keep a document open in many tabs and devices                                                                          |
| `COLLAB_MAX_CONNECTIONS_PER_DOCUMENT`                                      | 250                             | The handshake is refused (`too_many_connections`). Counted across instances                                                   | You measured that an instance holds more editors of one document (see the Performance section of the README)                 |
| `COLLAB_MAX_DOCUMENT_BYTES`                                                | 16 MiB                          | Writes are refused (`document_full`); reads continue, and updates that only delete are let through so the document can shrink | Memory per instance allows larger documents. | `COLLAB_MAX_PENDING_BYTES`                                                 | 8 MiB                           | The socket whose update would pass it is closed (`overloaded`). Persistence and checking:

| Variable                       | Default | Meaning                                                                                                                                        |
| ------------------------------ | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `COLLAB_COMPACT_EVERY_UPDATES` | 200     | Fold the log into a snapshot after this many updates. Lower: faster loads, more snapshot writes.                                               |
| `COLLAB_COMPACT_AFTER_MS`      | 30000   | Or this long after the first uncompacted update. A failed compaction is retried after this.                                                    |
| `COLLAB_UNLOAD_GRACE_MS`       | 30000   | How long a document stays in memory after its last client left. Higher: faster reopen, more memory.                                            |
| `COLLAB_RECONCILE_INTERVAL_MS` | 5000    | How often an instance reads the log for updates it did not see. This is the longest an instance can lag if the relay loses a message.          |
| `COLLAB_MEMBERSHIP_RECHECK_MS` | 60000   | How often sockets are compared with the `Membership` table. This is the longest a removed member stays connected if the Redis message is lost. |
| `COLLAB_ROLE_CACHE_MS`         | 1000    | A socket's role is read again before a write if older than this. Lower: a demotion bites sooner, more queries.                                 |
| `COLLAB_CONNECTION_TTL_MS`     | 45000   | A dead instance's connection slots expire after this.                                                                                          |

| --------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Sign-in, registration, "send the link again", invitations | "Too many attempts. Try again in N minute(s)." (HTTP 429, `rate_limited`)                  | A rate limit above was reached. It clears when the window ends. For an address that is locked out by someone guessing its password, the limit also applies to the owner; see the limits in SECURITY.md.                                                                                                                                                                                                                                                     |

| Verification link page                                    | "This link is invalid or has expired" (`invalid_token`)                                    | The link is used, older than 24 hours or replaced by a newer one. | Editor page                                               | "You are signed out" with a link to sign in                                                | The token request answered 401: the session ended. | Editor, connection indicator                              | "Syncing…"                                                                                 | Connected, exchanging state. Stays for long only if the server is slow to answer step 2, or if writes are being refused: see `document_full` below.                                                                                                                                                                                                                                                                                                         |
| Editor, connection indicator                              | "Reconnecting…", with "Your edits are kept here and will sync when the connection returns" | The socket closed and the client is retrying with a fresh token and exponential backoff. Causes: a deploy, a network drop, the collab server or Redis down, a handshake refused with `rate_limited`, `too_many_connections` or `server_error` (all retried), a socket closed for exceeding a rate limit or `overloaded`. If it never ends, read the collab server's log for the refusal reason.                                                             |
| Editor, connection indicator                              | "Offline" with a note about unsynced edits                                                 | The browser reports no network. Edits are kept in the local database and merge when it returns.                                                                                                                                                                                                                                                                                                                                                             |
| Editor                                                    | "View only" badge, no toolbar                                                              | The user's role is `viewer` (or was demoted while the page was open: the page switches without a reload).                                                                                                                                                                                                                                                                                                                                                   |
| Editor, nothing visible                                   | The indicator stays on "Syncing…" and typed text does not appear for others                | The server answered `rejected` with `document_full` (the document reached `COLLAB_MAX_DOCUMENT_BYTES`: delete content, which is still allowed, or raise the limit), `too_large` (one paste exceeded `COLLAB_MAX_UPDATE_BYTES`) or `forbidden`. This version's client does not show the `rejected` notice; the reason is in the collab server's log with the document, user and role.                                                                        |

Handshake refusals reach the client as a `connect_error` with a code, never the reason: `invalid_token` (bad, expired or foreign token), `not_a_member`, `too_many_connections`, `rate_limited`, `server_error` (the database or Redis could not answer). The reason is logged.

## Backups: PostgreSQL

Everything that must survive is in PostgreSQL. Redis can be lost without losing data.

- **Back up the whole database** with `pg_dump` (logical, for a database of this size) or continuous archiving (`pg_basebackup` plus WAL) if you need point-in-time recovery. A managed PostgreSQL service does the second for you.

  ```sh
  pg_dump --format=custom --file=collabdocs-$(date +%F).dump "$DATABASE_URL"
  pg_restore --clean --if-exists --dbname="$DATABASE_URL" collabdocs-2026-01-01.dump
  ```

- **A document is its latest snapshot plus the log rows after it** (`DocumentSnapshot`, `DocumentUpdate`). Back both tables up together, from one consistent dump; `pg_dump` is consistent by itself. A snapshot without the log rows after it loses the edits since the last compaction.
- **Edits since the backup are not lost to the clients.** A client that was connected keeps its copy in the browser's IndexedDB and sends what the server lacks at the next sync, so restoring an older backup does not delete work that an open client still has. A restore does reset memberships to the backup's state, so removed members return and new ones vanish: tell the owners.
- **Restore into an empty database,** run `npm run db:deploy` to make sure the migrations are current, then start the collab servers. Restart every collab instance after a restore, so that none holds a copy that is ahead of the database.
- **Test the restore.** A backup that has not been restored is a guess.

## When Redis goes down

The collab server does not wait for Redis, and the web app does not need it to serve pages.

- **Open sockets keep working** and edits keep being stored. Updates between instances are not relayed while Redis is down; each instance catches up by reading the log every `COLLAB_RECONCILE_INTERVAL_MS`, so with several instances editors on different instances see each other's changes within that interval, not instantly. Cursors on other instances freeze or disappear.
- **New connections are refused** with `server_error`, because the connection counters live in Redis; clients retry with backoff, and connect when Redis is back. A collab server that is started while Redis is down exits after `COLLAB_REDIS_CONNECT_TIMEOUT_MS`.
- **Membership changes are not pushed.** Removing a member still takes effect: a write re-checks the role in the database before it applies (within about a second), and the periodic re-check closes the socket within `COLLAB_MEMBERSHIP_RECHECK_MS`. A removed user cannot reconnect, because the handshake looks the membership up in the database.
- **The web app's rate limits fall back to the process:** each instance counts alone, so the cluster-wide limit is looser until Redis is back. The fallback never means "no limit".
- **Recovery is automatic:** the subscriptions resume by themselves when Redis answers. Nothing needs a restart. If Redis lost its data (a restart without persistence), nothing is lost either: the counters rebuild, and the log is in PostgreSQL.

## When PostgreSQL goes down

PostgreSQL is the only store of record, so this is the serious one.

- **Open sockets keep receiving and relaying edits for documents already loaded,** but a write that cannot be appended makes the instance drop that document from memory and disconnect its sockets. Nothing is relayed. The clients keep their edits locally ("Reconnecting…").
- **New connections fail** with `server_error`: the handshake looks the membership up. A write whose role cannot be confirmed closes its socket; the periodic re-check closes a document's sockets after three failed queries in a row.
- **The web app** answers 500 (`Internal server error`) from every route that touches the database, and sign-in fails (a JWT session is verified without the database, but every route looks the user up again). The pages that need no data still render.
- **Recovery:** when PostgreSQL is back, clients reconnect by themselves, reload the document from the database and send what it lacks, so edits made during the outage are merged, not lost, as long as the browser tab or its local database survives. Edits that sat only on an instance's memory at the moment it dropped the document are the ones to worry about, and for those the client's copy is the backup.
- **After a failover to a replica or a restore,** restart the collab instances (see Backups).

## Health and logs

- `GET /healthz` on the collab server answers 200 when it is up. It does not check the database.
- Both processes log JSON lines to standard output: `socket connected`, `socket disconnected` with the reason, rejected messages (document, user, role, event, reason, never content), dropped invitations, a failed compaction, a failed periodic re-check. Collect them where the processes run.
- Watch: the number of loaded documents per instance and the process memory (a document at the 16 MiB cap can need hundreds of megabytes; run instances with a memory limit), the size of `DocumentUpdate` (a log that only grows means compaction is failing), and the rate of `rate_limited` and `too_many_connections` refusals.
